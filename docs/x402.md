# Leash and x402

Leash's paid APIs speak **x402 v2** on the wire ([spec](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md), [HTTP transport](https://github.com/x402-foundation/x402/blob/main/specs/transports-v2/http.md)):

| Step | Header (base64 JSON) | Shape |
|---|---|---|
| Server → client, `402` | `PAYMENT-REQUIRED` | `PaymentRequired { x402Version: 2, error, resource, accepts: [PaymentRequirements] }` |
| Client → server, retry | `PAYMENT-SIGNATURE` | `PaymentPayload { x402Version: 2, resource, accepted, payload: { transaction } }` |
| Server → client, `200` | `PAYMENT-RESPONSE` | `SettlementResponse { success, transaction, network, payer, amount }` |

The facilitator implements the standard interface: `GET /supported`, `POST /verify`, `POST /settle`, with `{ x402Version, paymentPayload, paymentRequirements }` request bodies and `{ isValid, invalidReason, payer }` / `{ success, errorReason, transaction, network, payer }` responses. Networks use CAIP-2 ids (`solana:<genesis-hash prefix>`; devnet is `solana:EtWTRABZaYq6iMfeYKouRu166VU2xqa1`).

## What's different: the `leash` scheme

In the standard SVM `exact` scheme the client signs a plain SPL `TransferChecked` from its own wallet. With Leash, the agent doesn't own the money: the tokens sit in a vault owned by a policy PDA, and the agent can only move them by calling the Leash program's `spend`, which checks the policy and then makes the `TransferChecked` as a CPI.

`PaymentRequirements` for the `leash` scheme:

```json
{
  "scheme": "leash",
  "network": "solana:…",
  "amount": "50000",
  "asset": "<test USDC mint>",
  "payTo": "<service wallet>",
  "maxTimeoutSeconds": 120,
  "extra": { "programId": "5tbQ7LteAdDS9MTbLDqaZiHxiPsoY6EuXUoh3KBKN65n", "nonce": "<32-byte hex>", "expiresAt": 1794051451 }
}
```

The client puts `extra.nonce` into `spend`'s `request_id`, which ties the payment to one request. The payload is `{ "transaction": "<base64 v0 tx signed by the agent session key>" }`.

**`/verify`** (`services/facilitator.ts`):
1. Version, scheme and network match; the nonce matches `accepted`, hasn't expired, and hasn't been used.
2. The transaction holds **exactly one** Leash `spend`: mint = `asset`, destination = ATA(`payTo`, `asset`), amount ≥ `amount`, `request_id` = nonce.
3. Simulates with signature verification. If the policy rejects it, the response is `invalidReason: invalid_transaction_state` with the Anchor error name (for example `Leash policy rejected payment: PolicyPaused`).
4. The simulated `SpendEvent` must match the recipient, the amount and the nonce.

**`/settle`**: re-verifies, reserves the nonce, submits, waits for `confirmed`, then re-parses the onchain `SpendEvent` and checks it again. A replayed payload fails with `invalid_transaction_state: nonce already used`.

## What we tested against a public facilitator

`scripts/x402-spike.ts` builds a Leash `spend` shaped the way the SVM `exact` spec asks: a v0 transaction, `SetComputeUnitLimit` + `SetComputeUnitPrice`, the facilitator's `feePayer` as fee payer, and a partial signature from the agent. It POSTs this to `https://x402.org/facilitator/verify` (`solana:EtWTRABZaYq6iMfeYKouRu166VU2xqa1`, with `smartWalletSupported: true`). Result:

```
POST https://x402.org/facilitator/verify → HTTP 200
{"isValid":false,"invalidReason":"invalid_exact_svm_smart_wallet_program_not_allowed: 5tbQ7LteAdDS9MTbLDqaZiHxiPsoY6EuXUoh3KBKN65n","payer":""}
```

This is expected. `exact` on SVM accepts either a fixed instruction layout ("Any other program, anywhere in the sequence, MUST be rejected") or simulation-based verification restricted to an allowlist of smart-wallet programs (Squads, Swig, SPL Governance, …). PayAI's facilitator (`facilitator.payai.network/supported`) lists no Solana v2 kinds.

**Path to standard compatibility:** the spec's smart-wallet path already inspects inner (CPI) `TransferChecked` instructions in simulation. If Leash were added to a facilitator's smart-wallet program allowlist, the same transaction would pass as `exact`. Until then, the `leash` scheme runs on our own facilitator with the same interface.

## Smoke test

`npx tsx scripts/smoke-x402.ts` (services running): 402 → spend → retry → 200, then two replay attempts, one to the API and one straight to `/settle`. Both are rejected.
